# Introduction to DFX

**`dfx`** (DFINITY Execution tool) is the official command-line interface (CLI) for developing, testing, deploying, and managing smart contract canisters on the **Internet Computer (ICP)**.

Whether you write smart contracts in Motoko, Rust, TypeScript (Azle), or Python (Kybra), `dfx` acts as your compiler orchestrator, local replica manager, identity provider, cycles administrator, and mainnet deployment engine.

---

## What Does `dfx` Do?

| Function | Description | Typical Command |
|---|---|---|
| **Local Environment** | Boots an in-memory replica running a complete Internet Computer consensus simulation | `dfx start --background` |
| **Project Scaffolding** | Generates starter projects configured with backend and frontend canisters | `dfx new hello_world` |
| **Wasm Compilation** | Compiles code into WebAssembly (`.wasm`) and extracts Candid IDL (`.did`) | `dfx build` |
| **Identity & Security** | Manages cryptographic identities (ed25519 / secp256k1) and principals | `dfx identity whoami` |
| **Canister Deployment** | Installs, upgrades, and starts canisters on local replica or mainnet | `dfx deploy --network ic` |
| **Inter-Canister Calls** | Interacts with live methods using Candid text formatting | `dfx canister call my_canister greet '("World")'` |
| **Cycle Economics** | Converts ICP to Cycles and manages fuel reserves | `dfx cycles convert --amount 1.5` |

## Core Internet Computer Concepts in `dfx`

To effectively use `dfx`, you should understand the fundamental primitives of the Internet Computer:

### 1. Canisters
A canister is an evolution of a smart contract. It consists of:
- **WebAssembly Bytecode (`.wasm`)**: Compiled logic executed in a sandboxed, deterministic virtual machine.
- **Persistent Memory**: Linear memory and 64-bit stable memory that persists automatically between update calls and across code upgrades without an external database.
- **Canister ID**: A unique 27-character principal (e.g. `6vbhm-nqaaa-aaaan-q6muq-cai`) assigned to the canister.

### 2. The Reverse-Gas Model
Unlike traditional blockchains (e.g. Ethereum or Solana) where users must pay network gas fees for every interaction:
- Canisters hold their own fuel balance measured in **Cycles** ($1 \text{ Trillion Cycles} \approx 1 \text{ XDR} \approx \$1.30 \text{ USD}$).
- Queries and read requests are free and resolve in ~100ms.
- Update calls deduct cycles directly from the canister's reserve, allowing end users to interact without a crypto wallet or payment token.

### 3. Principals & Identities
- **Identity**: A local cryptographic key pair stored securely in `~/.config/dfx/identity/`.
- **Principal**: The public address representation derived from your public key (e.g. `2vxsx-fae...`).
- **Account Identifier**: A 32-byte hash used on the legacy ICP Ledger canister, derived from your principal and an optional 32-byte subaccount.

### 4. Candid Interface Definition Language (IDL)
Candid is the language-agnostic interface description language used on the Internet Computer:
- It defines canister method signatures, input parameters, and return types.
- `dfx` parses `.did` files to automatically validate commands and serialize JSON or Candid text into binary over HTTP boundary nodes.

## Local Replica vs. Mainnet

`dfx` commands operate by default on your **local replica** unless you explicitly specify `--network ic`:

```bash
# Targets the local replica running on 127.0.0.1:4943
dfx canister status my_canister

# Targets the live, global Internet Computer mainnet
dfx canister --network ic status my_canister
```

> [!TIP]
> You can also use the shorthand flag `--ic` in place of `--network ic`.

## Project Structure (`dfx.json`)

Every project managed by `dfx` contains a root configuration file named `dfx.json`. Here is a standard multi-canister configuration:

```json
{
  "canisters": {
    "backend": {
      "type": "motoko",
      "main": "backend/src/main.mo"
    },
    "frontend": {
      "type": "assets",
      "source": [
        "frontend/out"
      ]
    }
  },
  "defaults": {
    "build": {
      "packtool": ""
    }
  },
  "networks": {
    "local": {
      "bind": "127.0.0.1:4943",
      "type": "ephemeral"
    },
    "ic": {
      "providers": ["https://icp0.io"],
      "type": "persistent"
    }
  },
  "version": 1
}
```

Key directories generated by `dfx`:
- `.dfx/local/canister_ids.json`: Stores local canister IDs mapped to canister names.
- `canister_ids.json` (root): Stores production mainnet canister IDs.
- `.dfx/local/canisters/<name>/`: Contains compiled `.wasm` files and generated TypeScript declarations.

## The Standard Developer Workflow

1. **Start the local network replica**:
   ```bash
   dfx start --background --clean
   ```

2. **Create and register canisters**:
   ```bash
   dfx canister create --all
   ```

3. **Build and compile WebAssembly binaries**:
   ```bash
   dfx build
   ```

4. **Deploy the project locally**:
   ```bash
   dfx deploy
   ```

5. **Execute a query method (fast, read-only)**:
   ```bash
   dfx canister call backend getCounter --query
   ```

6. **Execute an update method (writes to state)**:
   ```bash
   dfx canister call backend incrementCounter
   ```

7. **Deploy to Mainnet**:
   ```bash
   dfx deploy --network ic
   ```
